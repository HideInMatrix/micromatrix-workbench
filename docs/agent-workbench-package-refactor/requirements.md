# Agent Workbench 包结构重构需求

## 1. 问题与目标

`agent_workbench` 根包目前同时承载桌面入口、配置模型、MCP 进程、Server/Gateway 生命周期、OAuth、更新、权限 Broker 和桌面 API。根目录文件数量与单文件体积已超过便于维护的范围，并且模块层级不能直接表达领域边界。

本次重构目标是按领域拆分模块和目录，在不改变现有用户行为、持久化数据、命令入口和安全边界的前提下，降低根目录噪音、单文件体积与跨领域耦合。

## 2. 用户故事

### US-1：代码导航

作为维护者，我希望从目录结构直接判断 Server、Gateway、OAuth、Runtime、Update 和 Desktop API 的归属，以便快速定位功能实现。

### US-2：稳定入口

作为现有调用方，我希望 CLI、桌面启动、内部 MCP Worker 和公开 Python 导入在重构后继续工作，以便升级不破坏现有部署和脚本。

### US-3：安全与行为等价

作为用户，我希望重构不改变 Permission Broker、Workspace 边界、OAuth、网络 Provider、Server/Gateway 生命周期和更新行为。

### US-4：可验证构建

作为发布维护者，我希望重构后的源码、桌面前端和 PyInstaller 包都能通过自动化验证。

## 3. 功能需求与验收标准

### R-1：领域目录

- `agent_workbench` 应按职责建立清晰子包，至少覆盖 `core`、`runtime`、`servers`、`gateways`、`oauth`、`updates` 和 `api`。
- 已存在的 `network`、`executables` 与 `web` 保持各自边界。

验收标准：

- 当维护者查看 `agent_workbench` 根目录时，系统应仅保留包入口、兼容入口和少量顶层编排模块。
- 当维护者查找 Server、Gateway、OAuth 或 Update 实现时，系统应提供唯一且语义明确的领域目录。

### R-2：大文件拆分

- `desktop_api.py` 应拆分为稳定 Facade 与按领域组织的 API 协作者。
- `gateway_launcher.py` 应拆分启动编排、诊断和 OAuth/路由验证等职责。
- `self_update.py` 应拆分更新编排、下载/校验和平台安装职责。
- 拆分应优先降低职责耦合，不以机械控制行数为唯一目标。

验收标准：

- 当桌面端调用既有 API 方法时，Facade 应保持原有方法名、参数和返回结构。
- 当 Gateway 启动、诊断或停止时，系统应保持现有执行顺序、回滚和错误语义。
- 当更新检查、下载或安装执行时，系统应保持现有校验与平台行为。

### R-3：兼容入口

- `python -m agent_workbench`、根目录 `desktop.py` 和内部 `agent_workbench.mcp_worker` 命令必须继续可用。
- `agent_workbench.__init__` 当前导出的公开类型必须继续可导入。
- 已公开或被项目外脚本引用的旧模块路径应通过薄兼容层保留；项目内部代码迁移到新路径。

验收标准：

- 当调用现有 CLI/桌面/Worker 入口时，系统应进入与重构前相同的主流程。
- 当调用方从 `agent_workbench` 导入现有 `__all__` 类型时，导入应成功且对象身份指向新实现。
- 当旧模块路径被导入时，兼容模块应只转发新实现，不复制业务逻辑。

### R-4：依赖方向

- 领域模型和配置不得依赖桌面 UI、管理器或进程启动实现。
- `network`、`servers`、`gateways` 等实现应依赖稳定的 core/runtime 接口，避免通过包 `__init__` 形成循环导入。
- 新子包 `__init__` 应保持轻量，不主动导入会产生进程副作用或循环依赖的模块。

验收标准：

- 当 Python 从干净解释器导入每个新子包时，导入应成功且不启动后台进程、网络请求或 UI。
- 当运行模块导入 smoke test 时，系统不应出现循环导入或部分初始化错误。

### R-5：数据与配置兼容

- Server、Gateway、OAuth、用户设置和 Workbench 资产的文件路径、schema 和读取语义不因目录移动而改变。
- 不迁移、不重写用户现有配置文件，除非后续发现明确必要且另行记录。

验收标准：

- 当重构后的程序读取重构前生成的配置 fixture 时，系统应得到等价领域对象。
- 当保存未修改的旧配置时，系统应保持当前 schema 和敏感字段处理规则。

### R-6：当前改动保护

- 当前工作树中 MCP 管理页中文化、服务页单 Workspace Profile 隐藏和网络字段中文化改动必须保留。
- 重构不得覆盖或回滚用户尚未提交的修改。

验收标准：

- 当重构完成后检查工作树时，上述 UI 行为和文案修改应仍然存在并通过现有测试。

### R-7：测试与发布验证

- 更新所有受影响的内部 import、测试 patch 路径、文档路径和打包入口。
- 增加新目录边界、旧兼容入口和无副作用导入测试。

验收标准：

- 当运行 Python 全量测试时，所有非平台限定测试应通过。
- 当运行前端测试与生产构建时，测试、TypeScript、Vue typecheck 和 Vite build 应通过。
- 当执行 PyInstaller smoke build 时，桌面入口、Web 资源和内部 MCP Worker 模块应被正确收集。
- 当运行服务器部署测试时，无头 Linux 部署入口与依赖边界应保持通过。

## 4. 约束

- 使用渐进迁移；每个阶段保持可测试、可回退。
- 不改变公开 API 的请求/响应结构。
- 不改变权限默认值、OAuth 协议、网络暴露范围或 Secret 存储规则。
- 文件移动和内容修改使用可审查的小批次完成。
- 不删除旧模块路径，直到兼容层和调用方迁移已验证。

## 5. 非目标

- 不重新设计桌面 UI 或服务管理产品流程。
- 不更改 MCP/OAuth 协议版本。
- 不更改 Server/Gateway 持久化 schema。
- 不借重构新增网络 Provider、权限模式或更新渠道。
- 不以本次重构为由统一重命名所有用户可见术语。

## 6. 完成定义

只有同时满足以下条件，本次重构才算完成：

1. 领域目录与依赖方向落实；
2. 三个最大职责文件完成实质拆分；
3. 稳定入口和旧导入路径保持兼容；
4. 当前未提交 UI 改动完整保留；
5. Python 全量测试、前端构建测试、服务器部署测试和 PyInstaller smoke 全部通过；
6. 设计、任务清单和目录说明文档与最终代码一致。
